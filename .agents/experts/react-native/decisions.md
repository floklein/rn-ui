## Settled

- **A toggle in a popup inside a toolbar joins the toolbar** (#80): the toolbar's contexts are carried across a popup's `Modal` like every adapter context (#131), so a toggle in a dialog's content joins the toolbar and takes a disabled group's state, as React's context gives it on the web.
- **One primitive definition for both hosts** (ADR 0001, #13, #22). The adapter reads the declarative slot fields and delivers `press`; it never runs `bind`, `asleep`, `connect`, the `on` handlers or the DOM writers. Native behavior lives in core's twins and native behavior files; core never imports `react-native`. Edits inside upstream's files are limited to the ADR's list, and each is in the registry.
- **Real native views, at parity** (#2, #15). Not React Native Web, no DOM layer, no native code in the adapter, no OS controls or native modules. Floor: React Native 0.88, New Architecture, Expo SDK 58, no Metro configuration.
- **Dependencies** (#16): `react` and `react-native` only, plus Gesture Handler in Drawer's entry and the sheet entry. Insets come from the app through `OverlayHost`.
- **Names follow `@ui-sdk/react`** wherever the concept exists (#20). Same subpaths, no root entry; an entry is absent only when nothing in it exists on native (today `shortcuts`). Web-only options and values are absent from the types (`container`, `shortcut`, `modal="trap-focus"`, `name`, `form`, the hidden `input` part, Pagination's `getHref`, ticket 87). Switch has no `value` (council batch 1, #125), removed in its own props; Checkbox, Radio and Toggle keep it, since it names an item in a group. Native-only names: `OverlayHost`, `interaction`, File Input's `pick`, `onExit`, `/sheet`.
- **Styling** (#18): every part takes `style`, `className`, `children` and `render`; the first three may be functions of state, resolved by the part. Styles merge as arrays, never flattened. No `data-*` or `dataSet`: each data attribute and CSS variable becomes a state field. `interaction` (`{ pressed, hovered, focused }`) is a separate argument. No styling library assumed; NativeWind v4 users call `cssInterop`.
- **Translation in one place** (#13, #30): core's ARIA in, `accessibility*` props out, never `role` or `aria-*`. A user's `accessibility*` props win field by field. `aria-controls`, `aria-owns` and `aria-activedescendant` are dropped: each option is its own accessible element.
- **A user's `role` and `aria-*` merge with core's as in `@ui-sdk/react`** (#128, found in ticket 85): core's attribute wins where it has a value, the user's stays where core's is `undefined`, and `yieldToAuthor`'s names are the user's. A Button or Toggle declares no role of its own on native (its element never binds, like a web `<button>`), so `<Button role="link">` is a link and `<Toggle role="switch">` a switch; a Separator or a tab keeps core's role. A user role React Native can't map (`group`) leaves the button role from `type="button"`.
- **iOS tab lists are tab bars** (council batch 2, #130): the translation gives core's `tablist` `tabbar` on iOS, the only role that sets `UIAccessibilityTraitTabBar`; the list stays a container, so each tab is still its own element. Android keeps `tablist` ("Tab List"). Recorded in the spec; the VoiceOver check is outstanding until a physical iPhone.
- **`presentation`/`none` yield on a pressable part** (council batch 2, #130): on a part whose default host is `Pressable` the translation ignores them, so `<Button role="presentation">` stays a button, as a browser keeps a focusable `<button role="presentation">` one. A `View` part becomes `none`. A user's explicit `accessibilityRole` still wins.
- **`<Toggle role="switch">` reads its state from `aria-pressed`** (council batch 2, #130): native announces on or off from `aria-pressed`, where the web's switch ignores it and announces no state. Recorded as a difference; no code change, and an app can still pass `aria-checked`.
- **A bar is named like a single element** (ticket 86): `isSingleElement` in `usePart` counts a part with the `progressbar` or `meter` role, so its Label part's text becomes its `accessibilityLabel`; on Android the description then joins the label and the value text.
- **Names and descriptions** (#30, built in ticket 63): plain-text children register under their id (`src/names.ts`, from `usePart`); `aria-labelledby` and `aria-describedby` resolve through `toNativeProps(…, names)` to `accessibilityLabel` and `accessibilityHint` on a single accessible element only (a `Pressable`, `TextInput` or `Text` unless `accessible` says otherwise), never on a container. An id without plain text gives no name at all, and a missing `aria-labelledby` id warns in development. A dialog is named by its title, which takes the focus request on open.
- **FieldSet and Field disable through context** (ticket 63): `DisabledContext` sets `formDisabled` in any store that has it, as a fieldset watcher does on the web; a checkbox in a group joins only a Field inside the group.
- **Focus** (#21): requests are never treated as observed. Popups request accessibility focus once mounted and return it to the trigger on close. Trapping is the `Modal`'s isolation, not a keyboard trap. No roving focus, arrow keys, Home, End or typeahead; core's roving `tabindex="-1"` is not forwarded.
- **Hardware keyboards** (#21): each OS's own navigation over correctly exposed elements, no native code for key events. Arrow keys in composites, shortcuts, a keyboard trap and Escape where the OS doesn't route it are a scope exception, revisited when React Native delivers key events to views in a stable build.
- **Popups** (#17): a popup modal at open renders in React Native's `Modal`, a non-modal one in the nearest host (`OverlayHost`, or the open `Modal`'s own host). Android back closes the topmost layer with the `"back"` reason.
- **Hosts** (ticket 66): a non-modal popup renders into the topmost open host when it shows, and stays there until it hides; with none, in place with a development warning. Providers between the host and the popup's root don't reach it (spec rule 8). A modal popup renders its `Modal` in place, keeping every provider, and is a nested `Modal` when its root is inside an open one; opened while a `Modal` it isn't inside is up, it renders as a nested `Modal` in that `Modal`'s host. Nested `Modal`s show on iOS (iPhone 17, iOS 27.3, `overlays.spec.ts`), where a sibling never does. `accessibilityViewIsModal` sits on a `Modal`'s host view, not the content, so it doesn't hide the popups the host renders beside the content. A press under a host goes through; the host reports it (`NativeInput.press`) with the popups whose content or trigger it landed in, and it dismisses non-modal layers down to the first modal one.
- **Forms** (#23): no form participation and no hidden input. `required`, `disabled` and `readOnly` stay in state; `required` and `readOnly` aren't announced. The adapter adds no words of its own to a label.
- **Presence** (#24): a part that animates out takes `onExit(done)`; a fixed two-second timeout; the adapter ships no animation. Panels expose their measured size as state. A part "animates" when its slot takes `keepMounted` (`usePart`, ticket 60); while it exits it is `inert`, so it's hidden and takes no touches, and it keeps its host.
- **Examples draw marks with views** (ticket 60): text inside an accessible part joins its name, so a ✓ glyph would be read and would change the name with the state.
- **Direction** (#32): read from `I18nManager` at startup, app wide. No direction for part of the screen.
- **Sources** (rule 5): `touch` for a press and Android back, `virtual` for the iOS escape gesture, an accessibility action, or a press while a screen reader runs.
- **Checking** (#19, #8, #119, device specs in `tests/native/`): the native pattern check from `@ui-sdk/react-native/testing` on a host tree with no renderer; Jest with React Native Testing Library; device specs with Appium, Android blocking and iOS reporting; no spec with a screen reader on, a manual pass per component instead (`contributing/native-manual-pass.md`). A missing VoiceOver pass may be recorded as outstanding.
- **Docs and examples** (#31): a sixth section, `react-native`; examples in `examples/components/<name>/react-native/` shown as code only, kept compiling by the playground; a per-part state table replaces the data attribute and CSS variable tables; `pnpm test:docs` skips native.
- **Budgets** (#33): a byte budget per native entry in `size-budget.json`, measured by `scripts/size.mjs` with `react` and `react-native` external and core included. No performance budget.
- **Upstream** (#35): a registry maps twins, native behavior files, reroutes and additive edits to upstream files and commits; `pending` is one list, read by the parity, size and example checks.
- **Keyboard focus findings** (#120). iOS: React Native 0.88.1 never reports Full Keyboard Access focus to JS. `RCTViewComponentView` bridges UIKit focus updates (`didUpdateFocusInContext`) to `onFocus` only under `TARGET_OS_TV`, and fires `onFocus` only behind `enableImperativeFocus`, off by default. Without native code `interaction.focused` stays off on iOS, as the docs say. Android: a disabled part is no Tab stop. The translation's `accessibilityState.disabled` makes React Native call `setEnabled(false)`, and Android's focus search skips disabled views (checked on an emulator). `focusable={false}` wouldn't help: `accessible` keeps the view focusable.
- **Native behavior files and member order** (#78): what a slot's `bind` orchestrates is a `NativeBehavior` in core, run from the part's view ref while it's mounted; a group member joins through `nativeElement(part)`, and `order.native.ts` sorts members by `NativeHost.compare`. The adapter compares views with `compareDocumentPosition`; where views can't compare (a test renderer), it falls back to the order of renders a parent drove. Toggle and Checkbox groups use it (#78, #122).
- **Container parts keep their view** (#125, council batch 1): a part that isn't pressed and has a role (core's, so an unlabelled `group` counts) or a label gets `collapsable={false}` in `usePart`, before the user's props. On an Android 16 emulator this kept each toggle group's members together and in order under Tab; an app's own layout `View`s still flatten, recorded in the spec's differences.
- **An `aria-disabled` part gives no press feedback** (#126, found in #77): a pressed part whose translated `accessibilityState.disabled` is true gets `disabled` on its host, before the user's props, so Pressability refuses the touch and draws no `android_ripple`; its `interaction` keeps `pressed` and `hovered` off, even if it turned disabled while held. It stays `accessibilityState.disabled` on Android, as the council decided.
- **Accessibility actions do what a press does** (#127, found in #88): on Android the translation declares `expand` on a collapsed `aria-expanded` part and `collapse` on an expanded one (React Native offers TalkBack the same one from the state, flips its native tag, and reports only declared actions); `usePart` presses the part under the `virtual` source when the action changes the state, and does nothing otherwise. A user's `accessibilityActions` join the translated ones. iOS declares none: VoiceOver has no expand action, and a declared one would be an unlocalized custom action. `activate` isn't declared: undeclared, it reaches `onPress` through the click on both OSes, while declaring it would replace the click with an event. `increment`/`decrement` and `escape` have no generic route (core steps values and dismisses in key handlers the adapter never runs), so Slider, Number Input and the popups route them to their api when they land. `checkPattern`'s disclosure pattern checks that the shown tree outside the button grows on expand and shrinks on collapse, after each activate and, on Android, each action, and that the button declares them; the generic action check demands a focus request only after escape, so each popup pattern checks its own focus requests on Android when it lands.
- **An image is one element** (#81): `role="img"` gets `accessible` on iOS, so VoiceOver reads it as one element, and `collapsable={false}` on Android, where `accessible` would make it a Tab stop and Fabric would otherwise flatten the view and its label away (TalkBack reads a labelled view). A part with `aria-hidden="true"` and `tabindex="-1"` (a read-only rating's radios; every other emitter is a hidden form input) gets `accessible={false}` and `focusable={false}`, since a `Pressable` stays focusable on Android without the second.
- **A mirrored icon's flip is in the translation** (#78): `data-mirror` becomes `transform: [{ scaleX: -1 }]` when `I18nManager.isRTL`, merged before the user's style, so a user's own `transform` wins, as any class wins over the web's lowest-layer rule.
- **The indicator's box follows React Native's `left` and `right` styles** (ticket 61): `activeTabLeft` and `activeTabRight` swap right to left when `doLeftAndRightSwapInRTL` is on, so `left: state.activeTabLeft` lands on the tab. A `translateX` driven from it is physical and would be wrong right to left; logical `activeTabStart`/`activeTabEnd` would change a public shape.
- **Drags keep the responder system; a same-axis `ScrollView` needs the app's `scrollEnabled`** (council batch 3, #71): a drag part becomes a responder in `usePart` (`responder(part)` in `native-host.ts`), and no drag uses Gesture Handler, which would still compete with a core `ScrollView`'s pan. On iOS Fabric a plain `ScrollView` scrolling the same way pans along with a responder inside it, so the app passes `scrollEnabled={!dragging}`, with `dragging` set from the drag part's `onResponderGrant`, `onResponderRelease` and `onResponderTerminate` (user responder props merge with the adapter's). A perpendicular scroll view needs nothing; the library's Scroll Area stops its own scrolling. Recorded as a difference, documented in each drag page.
- **Publishing** (#11): packed as `@rn-ui-sdk/*` tarballs with the fork's version; core gets a `dist/native` build with each twin in its module's place.
- **Label reaches a control through the adapter** (ticket 82): core's label press finds its control in the DOM, so `Label` registers its `htmlFor` (`useLabelFor` in `names.ts`) and presses what the control registered under its `id` (`controlsById`, through `useFieldControl`). Switch, Checkbox, Input, Textarea and Slider join; a radio group joins when its ticket adds it. Slider joins with its root's `id`: each thumb's input calls `useFieldControl` with it, so a `Label` for the slider names the thumbs without a name of their own and its press focuses the slider unless disabled. A control has one label, the one mounted last. Settled: this stays in the adapter, with no core `label.native.ts` twin through `NativeHost`.
- **The adapter's own contexts cross a popup's outlet** (ticket 131, rule 8): every context the adapter creates goes through `carry` (`src/carried-context.tsx`), and the outlet provides each again inside the `Modal` with the value it has where the part renders. The list is taken once per content mount, so a context made later never changes the providers' nesting (review finding, fixed). An app's providers still don't cross. A new adapter context must be made with `carry`; `test/dialog.test.tsx` scans the sources for one that isn't.

## Known and open (don't report again, check whether fixed)

- **The indicator box reads the container's border from its `style` only** (#79): a border set through `className` (NativeWind) or by a `render` host isn't seen, so the box is off by that border. Tabs' list and Segmented Control's root.
- **Slider, unchecked on a device** (ticket 71b): with `accessibilityValue.text` set, React Native may skip `TYPE_VIEW_SELECTED` after increment and decrement, so TalkBack may stay silent on adjust; Android's `RangeInfo` truncates fractional values (`asInt()`); iOS may leave a pan already started a few points off when `scrollEnabled` turns off mid-gesture; Hermes may keep its old default locale after a runtime language change (Expo keeps the activity). Android device specs, the Android keyboard step and iOS's run of the updated specs are owed.

- **A dialog's focus request on open may be overridden on iOS** (ticket 65): `dialogNative` asks for the title as the content's view mounts, before UIKit presents the `Modal`'s view controller, whose screen-changed notification may move VoiceOver elsewhere. Needs the VoiceOver pass.
- **The escape gesture goes to the topmost layer** (ticket 65): `onAccessibilityEscape` on a dialog's content calls `escape(api)`, which the layer twin delivers to the topmost open layer, not to the dialog the gesture reached. A modal dialog hides what's under it from VoiceOver, so this only matters for non-modal layers stacked by OverlayHost (ticket 11).
- **An outside press is observed from touch events** (ticket 66): a TalkBack double tap clicks with no touch, so it likely never dismisses a non-modal popup with `closeOnOutsidePress`. Unchecked on a device.
- **A popup opened from code while a modal one is open becomes its child** (ticket 66, from the layer twin's parent rule): closing the modal one closes it with `"parent-close"`, where the web keeps two independent dialogs.
- **A trigger naming an unmounted dialog's controller falls back to the dialog around it** (ticket 65): `useControllerTarget(controller, nearest)`, as on the web.
- **The presence change reaches every animated slot** (ticket 65): `usePart` treats a part whose state says `open: false` as leaving, which a popup's content needs while core holds it mounted; for disclosure panels `present` already turns false at the same time, but no test pins that.
- **A sibling `Modal` never shows over an open one on iOS** (ticket 65, device check on an iPhone 17 simulator): a dialog opened from code over another dialog's `Modal`, rendered as its sibling, stays invisible while its layer is pushed. OverlayHost (ticket 11) renders such popups inside the open `Modal`.
- **A `TextInput` part given `role="presentation"` becomes `accessibilityRole: "none"`** (#130 review, suspected): the yield follows the default host `Pressable` only, while a browser also keeps a focusable `<input>` a textbox. What VoiceOver and TalkBack say for a `TextInput` with role `none` is unchecked.
- **A step that turns disabled under Android keyboard focus throws focus away** (ticket 87): Next onto the last page, or First or Last, gets `accessibilityState.disabled`, so `setEnabled(false)` drops keyboard focus to the first focusable view, where the web keeps focus on the step (`aria-disabled` plus `keepFocus`). The Pagination page says so; a fix belongs in the translation or a twin, decided with the known item on `aria-disabled` and Android Tab order.
- **OTP Input's field lies over its slots** (#129, council batch 2): the transparent `TextInput` is the root's last child, so a long press anywhere on the code offers Paste. The slots are `View`s under it; the field's `onPressIn` picks the slot under `locationX` (the nearest one in a gap) from each slot's `measureLayout` against the root, minus the field's own, since groups and separators offset later slots. Fabric measures synchronously. A tap on the focused field selects at press-in, and one unfocused selects once the press ends, so a scroll starting on the code doesn't focus it. After a tap, core's `tapped` skips the caret the field puts under the finger; Android first echoes the selection JS set at press-in, which is let pass without ending the skip (#129 review). When the tap moves no caret the skip waits, and typing, focus or blur clear it. The field takes `onLongPress`, so Pressability doesn't press after a long press and close the Paste menu by selecting a slot.
- **Long press on the focused OTP field on Android may paste over the tapped slot's range** (#129 review, suspected): press-in selects the slot and Android echoes it before the long press, so Paste could replace that selection rather than what the menu shows. Needs a device; the Paste specs start empty or focused without a value.
- **OTP Input's field takes no `testID`, `onFocus`, `returnKeyType` or `keyboardAppearance`** (#106 review): its props match the web adapter's set (`id`, `autoFocus`, the naming `aria-*`), so tools that find views by `testID` can't reach it. Adding props is a public-shape change.
- **Arrow keys, Home and End in OTP Input are unchecked** (#106 review, suspected): the field's own caret moves and `selectText` probably maps it a slot at a time, as on the web; Full Keyboard Access's focus ring may be invisible inside the 0.011-opacity field. Both for the manual pass.
- **Native-only `checkPattern` names** (ticket 87): `img`, `separator` and `pagination` exist only in the native check, and aren't in the Settled native-only names. Add them there or take them through discuss-first.
- **Pagination's `list` role on Android** (ticket 87, suspected): `AbsListView` with no collection info; what TalkBack says for it waits for the TalkBack pass.
- **`aria-current` reaches a screen reader only as `page`** (ticket 87): the translation turns `aria-current="page"` into `accessibilityState.selected` unless the part sets `aria-selected`, so Pagination's current page reads as selected. Calendar's `"date"` (today) and Timeline's `"step"` are still dropped, since selected would mean the committed date there; Tree and Navigation Menu's `"page"` will read as selected. Each of those tickets decides whether that's right.
- **A labelled indeterminate bar's Android description ends in ", "** (ticket 86): React Native joins the label and the empty value text the translation sends so the old value clears. Dropping `text` would leave the old value; recorded in the spec.
- **Android rounds a bar's range to whole numbers** (ticket 86): `RangeInfo` uses `asInt()`, so a meter from 0 to 1 at 0.68 exposes 0 of 1. What TalkBack says from it beside the description is unchecked.
- **`textOf` in `host-tree.ts` skips a child hidden on either OS** (ticket 86): a user's iOS-only `accessibilityElementsHidden` drops that text from the name the check computes for Android. Passing `os` to `textOf` would fix it.
- **TalkBack's expand on a disabled disclosure trigger still flips the native expanded tag** (#127): core refuses the press, so React's `accessibilityState` doesn't change and nothing rewrites the tag; TalkBack may then read "expanded" until the state changes. The same holds for any refused or canceled change. Whether TalkBack offers actions on a disabled node is unchecked on a device.
- **Not every `aria-expanded` part expands on press** (#127 review): a tree item with `expandOnPress={false}` selects on press, so TalkBack's expand would select it, and a combobox or trigger-menu input has `aria-expanded` but no press, so it declares the action with nothing to handle it and the generic action check would fail it. Those components need their own route when they land, or the translation declares the actions only on a pressed part.
- **The expand handler reads core's `aria-expanded`** (#127 review, suspected): a user's own `aria-expanded` reaches the translation, so the declared action follows it while the handler checks core's. No part does this today.
- **The declared expand and collapse actions have an empty label** (#127 review, suspected): React Native sends `label: ""`; TalkBack probably names the standard ids itself. Not checked on a device.
- **A disclosure panel lays its children out in a measuring view** (ticket 88): `usePanelSize` passes the panel's flex container keys (`flexDirection`, `gap`, `alignItems`...) on to it, so a panel's layout reaches its children, but padding stays on the panel, and `panelHeight` doesn't include it. `panelWidth` follows the panel's width, since the measuring view stretches.
- **Whether `onLayout` reports each frame of a JS-driven height animation under Fabric is unchecked on a device** (ticket 88): the size at close after an interrupted opening reads the panel's last layout.

- **A read-only text field is disabled for screen readers and the keyboard** (ticket 62): `readOnly` sets `editable={false}`, which React Native turns into `isEnabled = false` on Android and `enabled = NO` on a single-line iOS field, so it's announced as disabled and leaves Tab's order. A multiline iOS field stays enabled. React Native has no read-only field that stays enabled; rejecting every edit instead brings up the keyboard. Documented on the Input and Textarea pages.
- **A shown password is a plain text field on Android** (ticket 104): `secureTextEntry={false}` clears the password variation and the field keeps only `autoCorrect={false}`'s no-suggestions flag, a hint some keyboards ignore. Android's own "show password" uses `TYPE_TEXT_VARIATION_VISIBLE_PASSWORD`, which `keyboardType="visible-password"` gives. Needs a device check of the keyboard's suggestions and of the hide, show, hide order before it's added (in the translation, for a shown password).
- **A secure field erases its text on iOS when typing resumes after it's hidden again while editing** (ticket 104, seen on a simulator): UIKit's behavior; Android and the web keep the text. Recorded in the spec's differences and on the docs page.
- **Password Input's `capsLock` is always `false`**: `TextInput` reports no modifier keys.
- **A change canceled mid-composition ends the composition** (ticket 62, not checked on a device): React Native reports no composition events, so a canceled `onValueChange` writes the old text back at once and kills an IME's composition. The web waits for it to end. The Input page warns against cancel for anything but directly typed characters.
- **Two fields in one InputGroup**: native reaches the one mounted last, the web the first in the DOM.
- **A controller's `focus()` on a disabled text field still moves the screen reader** to it; on the web it does nothing.
- **Tabs' `direction` stays `"none"` on native** (ticket 61): `selecting()` in `tabs.ts` reads `element("tab", key)?.getBoundingClientRect()`, undefined on native, so no part's `direction` moves and a panel can't slide by direction. A fix needs core to read a box from the host (a `NativeHost` shape change). Not yet a recorded difference in the spec.
- **The indicator's box is measured against the tab's parent** (ticket 61): a tab wrapped in another view, or a list rendered as a horizontal `ScrollView`, gets a box relative to that view, and `activeTabRight`/`activeTabBottom` come from the list's own size. `measureLayout` against the list would fix it.
- **A tab list's `aria-label` may reach no screen reader** (ticket 61): the list isn't flattened (its `onLayout` keeps it), but a label on a container that isn't an accessible element probably isn't spoken. Needs the manual pass.
- **An inline callback `ref` reruns a part's native behavior on every render** (#122): `mergeRefs` in `render-element.ts` returns a new function when a ref's identity changes, so `<Checkbox ref={(view) => …}>` leaves and rejoins its group each render. Correct, a little wasted work; the fix belongs in the adapter's ref merging, for every behavior.
- **A pending Button loses Android keyboard focus**: its `aria-disabled` becomes `accessibilityState.disabled`, which disables the view, so Space on a button whose action is pending moves focus to the first focusable view (seen on an emulator, ticket 58). The web keeps focus on it. Same question as the `aria-disabled` item below; `focusableWhenDisabled` does nothing for Android's Tab either.
- **Busy and mixed on Android only with a label**: Android writes both into the view's description and rewrites it only from a state that names busy (`BaseViewManager.setViewState`). So on Android the translation leaves `busy` out for a part with no `aria-label`, and sends `checked: false` for its mixed, which then reads as unchecked (tickets 58 and 60). A labelled part with `aria-busy` or a checked state always names `busy`, `false` when it isn't busy, so the description follows each change; without it a checkbox kept "…, mixed" after it was checked (seen on an emulator, ticket 60). Name a mixed checkbox with `aria-label`.
- **The first-frame flag may be cleared before its frame is on screen** (ticket 60): `startingStyle` clears on the next `requestAnimationFrame`, and Fabric commits on the UI thread, so a style transition might never see that frame. Needs a device check.
- **An error may be heard twice on Android** (ticket 63, not checked on a device): Field announces an error that appears or changes, and the error also joins the control's `accessibilityHint`, which TalkBack may re-read while it stays on the control.
- **A FieldLabel is its own TalkBack stop on Android** (ticket 63): a `Text` with `onPress` is focusable and clickable with no role. Check it in the manual pass.
- **A control's name can miss its first frame** (ticket 63): a label's text registers in a layout effect, so the control is named on the next render.
- **A text field's disabled state is always sent** (ticket 63): Android kept a `TextInput` disabled when `accessibilityState` went from `{ disabled: true }` to absent (seen on an emulator), so Input, Textarea and FieldControl always send it, as `!editable`: an explicit `false` enables a read-only field, which then takes typing (ticket 104, on a Pixel 9). Other parts that carry only `disabled` in their state may have the same bug when enabled again; not checked.
- **Shared names keep core's web wording in the docs tables**: the native types and `TypeTable`s leave out the web-only names (#120), but descriptions of shared ones still mention forms, like `defaultChecked`'s form reset, `disabled`'s `<fieldset>`, the `reset` and `restore` reasons that can't happen on native, Radio's `list-navigation` reason and `RadioGroupState.readOnly`'s arrow keys (the Radio page says so under its Reasons table).
- **The hidden form slots are listed by hand** in `use-primitive.tsx` (`FormInputOwner` and the excluded names): a new hidden input in core type-checks as a part until it's added there.
- **A disabled interactive part may still be a Full Keyboard Access stop on iOS**: `canBecomeFocused` (`RCTViewIsInteractiveAccessibilityElement`) accepts the `switch`, `checkbox`, `radio`, `tab` and other interactive roles without checking disabled. Not checked on a device.
- **Native `TypeTable`s drop rows by name** (`container`, `shortcut`, `name`, `form`), so a future table with a real `name` field, like a state type, would lose it.
- **A part that is only `aria-disabled` leaves Android's Tab order too**: the translation turns it into `accessibilityState.disabled`, which disables the view. Core uses `aria-disabled` alone where a disabled item should stay focusable; the components that do (menus, lists) need to decide this when they land.
- **Switch's basic example names the switch twice on iOS**: its visible `Text` sits outside the `Pressable` and is its own accessible element. Putting the text inside `Switch` would make one element and widen the press target.
- **The install commands name `@ui-sdk/*`**, which the fork publishes as `@rn-ui-sdk/*`; the docs follow upstream's names until the owner decides.
- **A loaded avatar image is no Tab stop on Android, and TalkBack reading it is unchecked**: `AvatarImage` keeps `accessible` false there, since `Image` turns `accessible` into `isFocusable` (ticket 84). TalkBack should read the `contentDescription` of a non-focusable view; it needs the manual pass.
- **The avatar fallback may flash a frame for a cached image**: `Image` reports `onLoad` asynchronously even from its cache, where the web knows at bind. Not checked on a device; a `delay` hides it.
- `scripts/check-packages.mjs` builds the adapter with `skipLibCheck: true`, since React Native's globals clash with `lib.dom` (ticket 17 revisits it).
- **A group container's `aria-label` may reach no screen reader** (#78, #81, #125): container parts now keep their view (`collapsable={false}`), and on an Android 16 emulator the Checkbox Group example's "Toppings" label appears on its `ViewGroup` in the accessibility tree, where before the container was flattened away; whether TalkBack reads it needs the manual pass. On iOS a rating's container is `accessible="false"` (device tree, #81). On Android a `testID` keeps the view but not its children, which are hoisted beside it as siblings, so even then it gives the members no context (#81). Rating's docs say to put the subject in `getValueLabel` meanwhile.
- **Kept container views are unchecked off Android's Tab order** (#125): on iOS a group's view that used to be flattened now exists with its role and label, which may change how VoiceOver groups its members; a hand-written part whose host isn't a React Native view (an SVG group) now receives `collapsable`. Neither checked.
- **A read-only rating's controller `focus()` asks for a hidden radio** (#81): the roving stop is still a radio, which `accessible={false}` puts out of reach, so the request does nothing. The web focuses the same `aria-hidden` radio; focusing the image would be core's roving focus to change.
- **Whether Android drew a ripple on a group-disabled radio before #126 is unproven** (#126 review): `setEnabled(false)` may already stop `RippleDrawable`'s ripple, leaving only its pressed layer. The owed device check (`fixtures/radio.tsx`, Theme and Large next to Small) should compare against the commit before the fix. A user's `disabled={false}` on a hand-written part brings the touch back while `interaction.pressed` stays off, as the user asked.
- **An inline `ref` callback on a group member rejoins the group on every render** (#78): `mergeRefs` is keyed by ref identity, so a new ref detaches and reattaches the view, running the behavior's cleanup and join again. Symmetric, untested.
- **In a test renderer, a member inserted between memoized siblings sorts last** (#78): views can't compare there, and only the inserted member renders. Devices order it by the view tree (the toggle fixture's "add-strike" spec).
- **A Label for a control that never joins gives no warning** (ticket 82 review, suspected): `htmlFor` pointing at a RadioGroup or FieldControl names and presses nothing, silently, where a missing `aria-labelledby` id warns.
- **A Label's own node isn't checked on a device** (ticket 82): that it's a TalkBack and Tab stop on Android, like FieldLabel, and whether Enter or Space on it reaches `onPress` (a partial Android keyboard run left focus on the City label after Enter, with the soft keyboard up; note 82).
