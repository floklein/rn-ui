---
title: Native Host
description: What core asks of React Native, and how a native adapter answers.
---

On React Native, a part is a view, not an HTML element. Core never imports `react-native`. When it needs something only the app's views can do, such as moving a screen reader's focus to a part, it asks the **native host**, which `@ui-sdk/react-native` implements.

You don't call anything here to use the components. This page is for building an adapter, or for reading what a native component does under the hood.

## The Host Interface

`@ui-sdk/core/native` exports the `NativeHost` type, `setNativeHost`, which registers the host, and `nativeHost`, which returns the one registered now, so a check can wrap it to see what core asks. `@ui-sdk/react-native` calls it once, as it loads:

```ts
import { setNativeHost } from "@ui-sdk/core/native"
import { AccessibilityInfo } from "react-native"

setNativeHost({
  focus(part) {
    const view = viewOf(part)
    if (view) {
      if (isTextInput(view)) {
        view.focus()
      }
      AccessibilityInfo.sendAccessibilityEvent(view, "focus")
    }
  },
  field: (part) => fieldInside(part),
  announce(text, priority) {
    AccessibilityInfo.announceForAccessibilityWithOptions(text, {
      queue: priority === "polite",
    })
  },
  compare(a, b) {
    return viewOf(a).compareDocumentPosition(viewOf(b)) & 4 ? -1 : 1
  },
})
```

- `focus(part)` requests accessibility focus on the part's mounted view, and starts editing when the view is a `TextInput`. The accessibility focus request is never treated as done: with no screen reader running, it moves nothing. A part with no view asks nothing, so a controller's `focus()` after its component unmounts does nothing.
- `field(part)` returns the text field rendered inside the part's view, a `NativeTextField`, or `undefined`. An InputGroup's presses reach its field through it, where the web finds the field in the group's element: a press on the group's text starts editing the field, and its Clear part empties the field and starts editing it.
- `announce(text, priority)` has the screen reader say `text`. On iOS, `"polite"` waits for what VoiceOver is saying and `"assertive"` interrupts it; Android has no such option. Core's `announce`, and a Button's `pendingAnnouncement`, go through it, where the web writes into a live region.

- `compare(a, b)` says where two mounted parts render: negative when `a` comes first. A group orders its members with it, like a toggle group's value, which lists the pressed toggles in the order they render. `@ui-sdk/react-native` compares the parts' views in React Native's view tree.

## Native Behavior

On the web, a slot's `bind` runs while its element is in the page, and does what needs the element: a toggle joins its group there. The native host never runs `bind`. A `NativeBehavior` from `@ui-sdk/core/native` restates it: one function per slot, which runs while a part of that slot is mounted and returns its cleanup.

```ts
import { toggleNative } from "@ui-sdk/core/native"
import { toggle } from "@ui-sdk/core/toggle"
import { createParts } from "@ui-sdk/react-native/primitive"
import { Pressable, View } from "react-native"

const parts = createParts(toggle, { root: Pressable, icon: View }, toggleNative)
```

`createParts` and `usePrimitive` take it as their last argument. `toggleNative` is Toggle's: while a toggle's root is mounted it joins its group, so the group knows its toggles in render order, refuses a disabled one and can focus one. `checkboxNative` does the same for a checkbox in a checkbox group, and `ratingNative` for each radio in a rating, so the rating focuses its checked radio. `tabsNative` is Tabs': while a tab is mounted it joins the tabs' roving group, so the tabs know their tabs in render order, select the first enabled one when nothing is selected and can focus the selected one. `collapsibleNative` is Collapsible's: while its panel is mounted it reports when the panel settles, so `onOpenChangeComplete` runs once an opening appears and once a closing's `onExit` calls `done`.

## Focus From a Controller

A controller's `focus()`, like Switch's or Input's, goes through the host. On the web it focuses the part's element. On React Native it asks the host to focus the part's view, which starts editing a text field. A toggle group's `focus(value)` does the same for one of its toggles.

## Presence

On the web, a part that animates out, like a checkbox's indicator, stays in the page until its CSS animations finish. React Native has no animation core can read, so the app says when an exit ends. A part whose slot takes `keepMounted` takes `onExit` on native, typed by `ExitProps` from `@ui-sdk/react-native/primitive`. When the part starts leaving, it calls `onExit` with `done`, and stays mounted until `done` runs or two seconds pass. Meanwhile it stays on screen, even where its slot would hide it, like a tab panel whose tab was just deselected, takes no touches and is hidden from screen readers. Its state gains `startingStyle` and `endingStyle`, the web's `data-starting-style` and `data-ending-style`. A part you build with `createParts` or `usePart` gets all of this from its slot. A native behavior hears when the part settles through `onSettled(part, listener)` from `@ui-sdk/core/renderer`: with `true` once it entered, and `false` once its exit ended, even after its view is gone.

## Checking a Native Component

`@ui-sdk/react-native/testing` checks a native component with no device, the way `@ui-sdk/core/testing` checks a web one. Each check takes the host tree your test renderer rendered and the OS, and imports no renderer: pass your renderer's `act` so each action renders.

```tsx
import { act, render, screen } from "@testing-library/react-native"
import { checkPattern } from "@ui-sdk/react-native/testing"
import { Platform } from "react-native"

await render(
  <Switch aria-label="Wi-Fi">
    <SwitchThumb />
  </Switch>
)
await checkPattern(screen.container, "switch", { os: Platform.OS, act })
```

- `checkPattern` takes the `"button"`, `"checkbox"`, `"disclosure"`, `"img"`, `"radio-group"`, `"switch"`, `"tabs"` and `"textbox"` patterns; `"button"` is native only, since the web check has no button pattern, and covers toggle buttons too: each needs a pressed state that activation flips. It checks roles, required states, names, one accessible element per item and hidden content, then performs the accessibility actions a screen reader user has and reads the state after each: activate everywhere, escape on iOS, expand and collapse on Android. Opening and closing must request accessibility focus.
- `checkDirection` renders the component left to right and right to left, performs each action, and checks both directions end the same.
- `checkCreation` checks that creating a primitive and rendering its parts reads no web global and asks the native host nothing.
